# 감독과 정지 위험 대응

결론: 시스템의 강제 정지와 한도 소진을 막기 위해, 앱 본체가 직접 프로세스 수명을 관리하고 자원을 조정하며 놓친 알림을 신호함 기반으로 처리한다.

본 문서는 이전 OMT 운영 중 실제로 발생했던 다섯 가지 정지 위험에 대한 앱 차원의 감독(Supervision) 구조를 정의한다.

## 1. 터미널 OOM 종료

OS의 메모리 부족(OOM) 킬러에 의해 워커나 PM 터미널 프로세스가 강제 종료되는 경우다.

- **감지 방법:** 자식 프로세스로 띄운 `orca terminal wait`가 비정상 종료 코드나 시그널(예: SIGKILL)로 종료됨을 감지한다.
- **자동 대응:** 해당 태스크의 동일한 워크트리 경로에서 터미널을 다시 띄우고 상태를 복구하여 재개(resume)한다.
- **사용자 알림:** 타임라인에 "메모리 부족으로 프로세스 재시작 중"이라는 시스템 메시지를 작은 배지로 표시한다.
- **대체 경로:** 3회 이상 연속으로 OOM 킬이 발생하면 태스크를 `stalled` 상태로 변경하고, 이사(Director)에게 실패 사실을 에스컬레이션하여 판단을 맡긴다.

## 2. 감시 프로세스 강제 종료

시스템 모니터링이나 킥오프를 감시하던 기존 CLI 프로세스가 사용자 실수나 호스트 업데이트 등으로 종료되어 감독을 잃는 경우다.

- **감지 방법:** 데스크톱 앱 본체가 감시자 역할을 직접 통합 수행하므로, 별도의 감시 프로세스를 둘 필요가 없다. (앱 프로세스가 죽지 않는 이상 감독은 유지됨)
- **자동 대응:** 앱은 부팅 시 `director-watch` 및 로컬 상태 파일을 읽어 기존 진행 중이던 킥오프 목록과 활성 터미널을 다시 캡처(이어받기)한다.
- **사용자 알림:** 앱 재실행 시 "이전 킥오프 상태를 복구했습니다"라는 스낵바 메시지를 표시한다.
- **대체 경로:** 로컬 상태가 손상되어 복구가 불가능할 경우, 워크트리의 `.omt/plan` 상태를 읽어 수동으로 남은 워크플로를 재시작하는 버튼을 표시한다.

## 3. 놓친 결정 요청

장시간 자리를 비운 사이 PM이나 이사가 사용자에게 확인을 요청했으나 타임아웃되어 워크플로가 지연되는 경우다.

- **감지 방법:** OMT의 `director-inbox` 명령을 주기적으로 폴링(또는 파일 시스템 이벤트 감지)하여 대기 중인 멘션이나 승인 대기 건을 찾는다.
- **자동 대응:** 폰의 모바일 클라이언트로 푸시 알림(Tailscale 연결 상태에서)을 밀어 보내고, 타임아웃 전까지 기다린다. 타임아웃이 임박하면 자동으로 킥오프를 중단 상태(Paused)로 전환하여 한도 낭비를 막는다.
- **사용자 알림:** 앱 UI 상단과 신호함 패널에 읽지 않은 결정 요청을 배지로 강조한다.
- **대체 경로:** 사용자는 알림 안의 버튼이나 앱 내 신호함에서 `director-reply`를 통해 즉시 승인·반려를 처리할 수 있다.

## 4. 할당량(Quota) 소진 시 계정 전환

API 토큰 쿼터나 Agy/Claude 요금제 한도(예: 5시간 롤링 제한)에 도달하여 모델 호출이 멈추는 경우다.

- **감지 방법:** 모델 호출이 권한 거부(429 Too Many Requests 등) 또는 쿼터 소진 에러로 실패함을 OMT 런타임 결과나 로그를 통해 감지한다.
- **자동 대응:** OMT 2.8.5~2.8.6에 추가된 계정 풀(pool)과 handoff 기능을 호출하여 다음 가용 구독으로 태스크를 인계한다. 컨테이너 기반 격리를 사용할 때는 소진된 버킷과 연결된 격리 실행기를 내리고, 백업 격리 실행기로 전환한다.
- **사용자 알림:** 채팅창 상단의 여유 메모리 및 할당량 상태 바에서 소진된 계정을 빨간색으로 표시하고, "한도 도달로 2번 계정으로 전환함" 메시지를 띄운다.
- **대체 경로:** ADR 0006의 결론에 따라, 컨테이너 기반 전환이 기본이지만 컨테이너를 쓸 수 없는 환경에서는 홈 환경변수(`CLAUDE_CONFIG_DIR`, `CODEX_HOME` 등)가 통하는 CLI에 한정하여 디렉터리를 변경해 띄우는 방식으로 우회한다. OMT의 OpenCodex 프록시 격리 기능 또한 기존 고정 계정이나 macOS 환경이라면 보완적으로 사용될 수 있다.

## 5. 메모리 부족 시 자원 슬롯 조정

한 PC에서 여러 킥오프나 여러 워커가 동시에 돌 때 전체 메모리가 부족해져 전체 시스템 멈춤을 유발하는 경우다.

- **감지 방법:** OS API(호스트 메트릭)를 통해 시스템 여유 메모리를 실시간으로 읽고, 0.5GB 이하로 떨어지는지 모니터링한다.
- **자동 대응:** 여유 메모리가 기준치 이하로 떨어지면 앱은 OMT의 `resource-acquire` 슬롯을 일시적으로 축소(예: 병렬 워커 4개 → 1개)하고, 새 프로세스 실행을 지연 대기(Queued)시킨다. 메모리가 확보되면 큐를 다시 연다.
- **사용자 알림:** 상단 상태 바의 메모리 지표가 주황색/빨간색으로 점멸하며, 대화 목록에 "메모리 부족으로 새 작업 대기 중"이라는 안내를 표시한다.
- **대체 경로:** 슬롯 축소 후에도 5분 이상 메모리 압박이 지속되면 앱 자체의 웹뷰 메모리 누수를 방지하기 위해 사용하지 않는 백그라운드 DOM과 과거 대화 컨텍스트 캐시를 비운다.
