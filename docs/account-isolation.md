# 계정 격리 실행기 설계

결론: 오픈 소스 환경의 다양한 호스트(macOS, Linux, Windows)에서 계정 자격 증명을 확실하게 분리하기 위해, 초경량 컨테이너 기반 격리 계층을 도입하고 호스트 환경에 맞게 대체 가능한 런타임을 제공한다.

## 배경 및 참고 구현

사용자 제안(브리프 10번)에 따라 다중 계정(예: 업무용/개인용 등 성격이 다른 계정 사이) 전환 시 로그인 정보 충돌을 막기 위해 컨테이너 격리를 기본 방식으로 삼는다.

이 설계는 `inho-team/workbench` 저장소의 실측과 결정을 인용한다.
- **실측 (S13, 16부 구독 설계):** Agy CLI의 OAuth 할당량은 OS 사용자 및 키체인 단위로 묶여 있어 호스트의 홈 환경변수(`HOME` 등) 변경만으로는 계정 분리가 보장되지 않는다. (`workbench/spikes/s13-agy-permission/RESULT.md`, `workbench/docs/16-구독-설계.md` 인용)
- **참고 구현 (M-14):** `workbench/docker-compose.agy.yml` 및 `workbench/deploy/agy/Dockerfile`, `workbench/internal/node/agy.go`에 구현된 바와 같이, 계정마다 컨테이너를 하나씩 띄우고 로그인 정보는 호스트 디렉터리를 볼륨 마운트하여 영구 보존(1회 브라우저 로그인)한다. 컨테이너는 `sleep infinity`로 상시 가동하고 매 턴마다 `docker exec -i -w <작업 공간>`으로 진입하여 프로세스를 실행한다. 이때 작업 공간은 호스트와 동일한 절대 경로로 마운트하여 경로 일치 문제를 회피한다.

## 다중 호스트 지원 및 문제 해결

omt-console은 오픈 소스이므로 특정 호스트에 묶이지 않고 다중 호스트를 지원해야 한다.

- **macOS:** 유휴 메모리 절약을 위해 OrbStack을 우선 권장한다. (Docker Desktop 대비 메모리 비용과 속도에서 우위)
- **Linux:** 데몬이 없고 rootless 실행이 가능한 Podman이나 기본 Docker를 사용한다. 절대 경로는 그대로 일치한다.
- **Windows (WSL2):** Docker Desktop 구동 시 백그라운드 VM이 약 1~2GB의 메모리를 선점하므로, 이 PC와 같이 메모리가 부족한 환경에서는 부담이 될 수 있다. 이 경우 Docker Desktop 없이 `wsl --import`를 통해 계정마다 가벼운 WSL2 배포판을 직접 만들어 사용하는 것이 대안이 될 수 있다. 경로 일치 문제는 호스트의 드라이브(예: `C:\Users\...`)를 WSL 내 동일한 마운트 포인트(`/mnt/c/Users/...`)로 매핑하고 CLI 실행 시 이를 치환하는 래퍼를 두어 해결한다.

### 대체 동작
컨테이너 자체를 구동할 여력이 없거나 지원하지 않는 호스트에서는:
- 계정을 하나로만 고정하여 실행한다.
- 혹은 Agy가 아닌, 홈 환경변수(`CLAUDE_CONFIG_DIR`, `CODEX_HOME` 등) 변경만으로 분리가 확인된 CLI에 한정하여 구동한다.

## 더 가벼운 격리 방식 비교표

다양한 격리 런타임을 메모리 비용, 지연, 경로 일치 등 7가지 기준으로 비교한다. (수치는 공개 자료 및 S13, M-14 실측 기반)

| 방식 (런타임) | 유휴 메모리 | 계정 추가 시 메모리 | 턴 시작 지연 | 자격 분리(키체인) 보장 | 경로 일치 여부 | 설치 난이도 | 라이선스 및 상업 사용 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **OrbStack** (macOS) | 매우 낮음 (~50MB) | 낮음 (~10MB) | 없음 (exec) | 보장됨 | 보장됨 (호스트-컨테이너 1:1 마운트) | 매우 쉬움 | 유료 (상업용 라이선스 필요) |
| **Docker Desktop** (macOS/Win) | 높음 (1~2GB VM) | 낮음 (~10MB) | 없음 (exec) | 보장됨 | Windows는 마운트 변환 필요 | 매우 쉬움 | 유료 (대규모 기업 상업용 제한) |
| **Colima / Lima** (macOS) | 보통 (~500MB VM) | 낮음 (~10MB) | 없음 (exec) | 보장됨 | 보장됨 | 중간 | 오픈 소스 (MIT/Apache 2.0) |
| **Podman** (Linux) | 0 (데몬 없음) | 낮음 (~10MB) | 미확인 | 보장됨 | 보장됨 | 쉬움 | 오픈 소스 (Apache 2.0) |
| **Apple `container`** (macOS 26+) | 미확인 (경량 VM 기반) | 미확인 | 미확인 | 미확인 | 보장됨 | 중간 (최신 OS 요구) | Apple 독점 |
| **WSL2 직접 배포판** (Windows) | 보통 (~500MB VM 공유) | 낮음 (~10MB) | 미확인 | 보장됨 | 변환 필요 (`/mnt/c/...`) | 높음 (수동 세팅) | 오픈 소스 / Windows |
| **nsjail/bubblewrap** (Linux) | 0 (네임스페이스만) | 거의 0 | 없음 | 보장됨 | 보장됨 | 매우 높음 | 오픈 소스 |

### 호스트별 권장 조합 결론
- **macOS:** 라이선스 문제가 없다면 OrbStack, 무료 및 완전 오픈 소스 지향 시 Colima.
- **Linux:** Podman (가장 가볍고 보안이 뛰어남).
- **Windows:** WSL2 배포판 직접 분리 (Docker Desktop의 무거운 VM 오버헤드 회피).

격리 실행기 계층은 인터페이스로 추상화되어 위 조합 중 하나를 선택적으로 교체해 띄울 수 있다.

## Orca 프로세스 인식 충돌과 대안

**문제:** Orca는 터미널에서 실행 중인 전경 프로세스의 이름(`isTerminalRunningAgent`, `isShellProcess`)으로 에이전트를 인식한다. 컨테이너 턴 진입 시 `docker exec -i ...`를 호출하면 전경 프로세스가 `docker`가 되어, Orca가 이를 OMT 에이전트 워커로 올바르게 판정하지 못할 가능성이 높다. (`oh-my-teams/docs/plan/agy-terminal-path.md` 참고)

**대안 및 과제:** 이 충돌 여부를 Phase 1의 선행 실측 과제로 둔다. 만약 `docker exec`가 에이전트로 인식되지 않는다면, 격리된 컨테이너 계정은 OMT의 headless 경로(대시보드 세션 등)와 짝지어 백그라운드로만 돌리고, Orca 터미널을 열어야 하는 PM과 이사 역할에는 로컬 네이티브 프로세스를 할당하는 방식으로 타협한다.

## 오픈 소스 프로젝트로서의 전제

저장소를 공개하기 위해 다음 규칙을 준수한다:
1. **비밀 및 개인 경로 배제:** 소스 코드나 문서에 특정 사용자 이름(예: `kjsun`), 개인 홈 경로, 토큰, 비밀 값을 하드코딩하지 않는다.
2. **로그인 격리:** 로그인 정보(OAuth 토큰 등)는 호스트에서 컨테이너 이미지로 복사(COPY)하지 않으며, 컨테이너 내 볼륨 마운트를 통해 최초 1회 수동 로그인(device code 등)하여 로컬에만 보존한다.
3. **사용 목적 제한:** 다중 계정 기능은 개인용/업무용처럼 성격이 명확히 다른 계정 전환 용도로만 설계하며, 기본 설정은 꺼 둔다. 개인 계정을 여러 개 생성하여 할당량을 회피하는 행위는 약관 위반일 수 있음을 UI 및 문서(README, 약관 고지)에 명시한다.
4. **라이선스 문제:** 컨테이너 이미지에 서드파티 CLI(예: Agy, Codex) 바이너리를 포함하여 재배포하는 것이 해당 도구 라이선스에 위배되는지 확인한다. 만약 재배포가 제한된다면(미확인 시 안전하게), Dockerfile 작성 시 빌드 시점에 curl 등으로 직접 다운로드하는 방식으로 구현한다.
5. **글로벌 지원:** 오픈 소스 배포를 위해 README.md를 포함한 핵심 설계 문서는 향후 영어 버전도 함께 제공하기로 결정한다.

## OMT에 요청할 변경

OMT의 기존 프로필 스키마는 `command` 필드에 실행 파일 이름 하나만 허용하므로 컨테이너 실행 명령(`docker exec -i -w ...`)이나 래퍼 스크립트를 제대로 처리하지 못한다. 이를 해결하기 위해 `runner: { kind: "container", ... }` 형태의 명세를 지원해야 한다. 해당 요구 인자와 검증 조건 등 정본 절은 [OMT 연동 계약 문서](omt-contract.md)의 "OMT에 요청할 변경" 절로 분리하여 관리한다.
