# 아키텍처

결론: omt-console은 데스크톱 네이티브 앱(Tauri)이 본체가 되어 로컬 OMT 런타임과 Orca CLI를 직접 제어하며, 모바일은 데스크톱 본체에 원격 접속하는 클라이언트-서버 구조로 동작한다.

## 시스템 구성 요소 및 경계

omt-console은 사용자가 OMT(Oh My Teams) 환경을 채팅 형태로 다루기 위한 프론트엔드입니다. 시스템은 크게 세 가지 경계로 나뉩니다.

1. **데스크톱 본체 (Tauri + React 앱):**
   - 사용자 인터페이스를 담당하고 호스트 OS와 상호 작용합니다.
   - OMT 런타임(`teams-org.mjs`)과 Orca CLI 바이너리를 자식 프로세스로 실행합니다.
   - 원격 모바일 앱의 접속을 처리하는 로컬 API 서버 역할을 겸합니다.
2. **OMT 및 에이전트 런타임 (CLI 프로세스 묶음):**
   - Orca CLI를 통해 PM 및 워커(Worker) 터미널을 열고 관리합니다.
   - 이사(Director) 역할을 하는 모델은 OMT 헤드리스 런타임에서 실행됩니다.
   - 계정 격리 실행기 계층을 통해 작업과 모델 컨텍스트를 분리합니다.
3. **모바일 클라이언트 (Capacitor 앱):**
   - 데스크톱 본체와 같은 React 화면 컴포넌트를 사용합니다.
   - Tailscale을 통해 데스크톱 본체 네트워크에 접속하고 토큰으로 인증하여 원격 제어합니다.

## 프로세스 및 데이터 흐름

### 1. Orca 및 OMT 직접 호출 구조

데스크톱 앱 본체는 워크트리 환경에서 직접 CLI 명령을 띄워 에이전트를 감독하고 소통합니다.

- **터미널 제어:** PM과 워커 프로세스는 `orca terminal send`, `orca terminal read`, `orca terminal wait` 명령을 호출하여 메시지를 전달하고 상태를 읽습니다. (출력 형식 등 상세 내용은 [OMT 계약](omt-contract.md) 참조)
- **감독 및 킥오프 제어:** 앱은 OMT 런타임의 다음 명령들을 직접 호출합니다.
  - `director-signal`: 이사에게 킥오프 시작 등의 신호 전송
  - `director-inbox`: 놓친 결정 요청이나 멘션을 확인
  - `director-reply`: 승인/반려 등 멘션에 대한 응답
  - `director-watch`: 킥오프 상태 모니터링
  - `resource-acquire`: 여유 메모리와 자원 슬롯에 맞춘 작업 투입 허가

### 2. 이사(Director) 세션과 대화 구조

사용자의 메인 채팅 상대는 OMT 조직의 이사(Director) 역할입니다. 사용자가 앱에서 입력한 채팅은 이사에게 전달되며, 이사가 킥오프 지시, 분해, 리뷰 등의 역할을 수행합니다.

- **헤드리스 런타임 실행:** 이사 세션은 `claude -p --resume` 명령을 활용하여 OMT headless 런타임에서 실행됩니다. (관련 결정 사항: [ADR-0005](decisions/0005-director-session.md))
- **검토 결과:** 이 방식은 입출력을 스트리밍 JSON(`stream-json`) 형태로 주고받게 합니다. `init`, `step_update`, `result` 이벤트를 파싱하여 실시간 타이핑 효과, 툴 호출(`tool_name`, `tool_info`), 비용(`usage`) 등을 안정적으로 화면에 반영할 수 있습니다. (출력 스키마 상세 미확인, 추후 계약 문서 보완)

### 3. 계정 격리 계층

비용 한도 및 토큰 소진에 대응하기 위해 앱은 **계정 격리 실행기**를 거쳐 에이전트 프로세스를 띄웁니다.

- 앱은 이 계층을 인터페이스(교체 가능한 계층)로 추상화하여, 호스트 환경에 따라 컨테이너(OrbStack, Docker) 기반 격리나 로컬 홈 환경변수 방식 등으로 유연하게 교체할 수 있도록 설계합니다.
- 자세한 구조와 설계는 [계정 격리 설계](account-isolation.md) 문서에서 다룹니다.
