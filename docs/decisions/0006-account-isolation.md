# 계정 격리 방식

결론: 계정 격리의 기본 방식은 컨테이너(가벼운 런타임 활용)를 사용하고, 대체 경로로 홈 환경변수 방식(`CLAUDE_CONFIG_DIR`, `CODEX_HOME`)을 통하는 CLI에 한정하여 적용한다.

## 맥락

할당량 소진 시 대응을 위해 여러 계정(예: 업무용, 개인용) 간 전환이 필요하다. 계정별 자격 증명을 확실히 분리하면서 메모리 유휴 비용이 낮은 격리 방법이 요구된다.

## 대안

1. **컨테이너 (선택)**: 계정별로 컨테이너를 띄우고 호스트 볼륨을 물려 자격 증명을 분리한다(`sleep infinity` 기반 1회 로그인, 턴마다 `docker exec`).
2. **호스트 홈 환경변수**: `CLAUDE_CONFIG_DIR`, `CODEX_HOME`을 계정별로 설정.
3. **OpenCodex 프록시**: OMT의 프록시 활용.
4. **OS 사용자 분리**: 호스트 로컬 계정을 여러 개 만듦.

## 결정

컨테이너 방식을 기본으로 선택하며, 격리 실행기를 교체 가능한 계층으로 설계한다.

## 근거

- **컨테이너 안의 자격 증명 파일화**: 리눅스 컨테이너 안에서는 Agy, Claude, Codex 세 CLI 모두 자격 증명을 파일로 저장하므로 안전하고 확실하게 분리된다.
- **Agy와 홈 환경변수의 한계(S13 실측)**: Agy의 OAuth 할당량은 OS 사용자 및 키체인 단위로 묶이기 때문에 호스트 환경변수만으로는 분리되지 않는다.
- **OpenCodex의 한계**: OpenCodex 프록시는 Codex, macOS 환경 및 고정 계정에 한정되어 다중 호스트 오픈 소스 프로젝트에 적합하지 않다.
- **OS 사용자 분리의 문제점(M-14)**: 파일 소유권(UID) 충돌 및 sudoers 관리 복잡성이 발생한다.

## 결과 및 감수하는 위험

- **장점:** 서비스 정의(compose) 복사만으로 확장이 가능하며, 호스트 오염 없이 확실하게 계정이 분리된다.
- **다중 호스트 비용(Windows/macOS):** 리눅스가 아닌 호스트에서는 가상 머신(VM) 기반 런타임(예: Docker Desktop)이 추가 메모리를 사용한다. 이를 해결하기 위해 메모리 비용이 적은 대체 런타임(OrbStack, WSL 직접 사용 등)을 권장 조합으로 사용한다.
