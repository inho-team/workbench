# 효율 예산

이 문서는 새 workbench 설계가 도달해야 할 자원 및 속도 목표를 규정한다. 무거운 Orca 데스크톱 앱을 덜어내고, 경량 헤드리스 실행과 효율적인 결합 체계를 통해 메모리 고갈과 응답 지연을 해소하는 것이 핵심이다. 호스트 구동에 필요한 절대적인 메모리 상한과 지연 시간을 통제하여 원활한 다중 에이전트 환경을 보장한다.

## 예산 지표 및 목표

다음 예산표는 시스템이 반드시 지켜야 할 자원 소비 상한선과 속도 목표다. 효율이 최우선 기준이며, 아직 측정하지 못한 값은 "미측정"으로 둔다.

| 지표 | 현재 값 | 목표 값 | 목표 근거 | 측정 방법 (시점·도구·반복 수·환경 조건) |
|---|---|---|---|---|
| **유휴 메모리** | 1.1~2.5GB | **100MB 이하** | 현재 시스템의 여유 메모리가 0.5GB 미만인 상황을 극복하기 위해 역산한 값. | [환경] 작업 중인 에이전트가 없는 유휴 상태, [시점] 구동 후 5분 대기 직후, [도구] OS 명령(`ps -o rss=` 등)으로 전체 시스템 또는 데몬 프로세스의 상주 메모리 확인, [반복] 3회 측정 평균. |
| **에이전트 1개당 추가 메모리** | 약 300MB | **50MB 이하** | 단일 PC에서 최소 5개의 다중 에이전트(PM, PL, Senior, Junior, Research)를 동시 구동하기 위한 예산 한도. | [환경] 에이전트 워크플로 실행 중, [시점] 워커 프로세스 초기화가 끝나고 입력 대기 상태에 진입한 직후, [도구] OS 명령으로 생성된 워커 프로세스 상주 메모리, [반복] 5개의 에이전트 구동 후 각각 측정 평균. |
| **턴 시작 지연** | 미측정 | **500ms 이하** | 근거 없음 (사용자 경험 개선을 위해 임의 설정). | [환경] 단일 에이전트 구동, [시점] 워커 실행 명령 시점부터 모델이 응답을 시작하여 `stdout` 파이프에 첫 바이트가 수신되는 시점까지, [도구] 런타임 로그 내 타임스탬프 차이, [반복] 10회 평균. |
| **의사 신호 전달 지연** | 미측정 | **100ms 이하** | 근거 없음 (IPC 또는 이벤트 폴링 지연 최소화를 위해 임의 설정). | [환경] 다중 에이전트 동작 중, [시점] 의사(Director)가 신호 이벤트를 파일이나 소켓에 기록한 시각과 대상 에이전트가 이를 낚아챈 시각의 차이, [도구] 이벤트 타임스탬프 로깅, [반복] 100회 발송 평균. |
| **자원 부족 멈춤 빈도** | 여유 0.5GB 미만일 때 자주 발생 | **0회** | 사용자의 개발 작업이 시스템 자원 부족으로 차단되지 않기 위한 절대 조건. | [환경] 다중 에이전트 5기 동시 워크플로 수행을 1시간 유지, [시점] 실행 도중 언제든지, [도구] OS 커널 로그(OOM Killer 기록) 및 OMT 런타임 타임아웃/429 에러 로그 발생 횟수, [반복] 1시간 단위 3회 진행. |

## 계정 격리 효율

legacy M-14 (`legacy-workbench/docs/16-구독-설계.md`) 문서 서술에 따르면 OrbStack이 Docker Desktop 대비 RAM을 1/5 수준으로 적게 사용하며 유휴 CPU를 거의 점유하지 않는다고 한다. 이는 직접 측정된 값은 아니지만, 효율 예산을 맞추기 위해 무거운 VM 기반 도구를 지양하고 경량 실행기를 채택하는 설계의 주요 서술 근거로 활용한다.
